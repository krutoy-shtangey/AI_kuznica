# Контракты интеграции

Backend получает объект, реализующий `shared.contracts.Retrieval`. Методы синхронные. Если обработчик FastAPI асинхронный, backend выносит блокирующие вызовы за пределы цикла событий. Retrieval импортирует общие типы из `shared.contracts`.

## Идентификаторы областей

| Измерение | Идентификатор | Название |
| --- | --- | --- |
| Подразделение | `ib` | Дирекция ИБ |
| Подразделение | `tech` | Техническая дирекция |
| Подразделение | `dbrct` | ДБРЦТ |
| Этап | `presale` | Пресейл |
| Этап | `implementation` | Реализация проекта |

Это начальные справочники. В Python идентификаторы — строки, неизвестное значение — `None`, в JSON — `null`. Новые идентификаторы и синонимы добавляются в согласованные справочники без изменения типов. Backend приводит пользовательские названия и синонимы к каноническим значениям перед поиском. Если синоним указывает на несколько значений, контекст остаётся неподтверждённым.

## Поиск

```python
ScopeFilter = str | tuple[str, ...] | None

def search_documents(
    self,
    question: str,
    top_k: int = 8,
    department: ScopeFilter = None,
    stage: ScopeFilter = None,
) -> list[SearchResult]: ...
```

- `question` — непустой текст запроса с учётом уточнений. `top_k` — положительное целое число, максимум результатов. Ошибочный аргумент отклоняется через `ValueError`. Backend проверяет аргументы до вызова.
- Каждый фильтр принимает один идентификатор, непустой кортеж возможных идентификаторов или `None` для поиска без ограничения по этому измерению. Внутри кортежа действует «или», между измерениями — «и». Пустой кортеж и идентификатор вне согласованного справочника отклоняются через `ValueError`.
- Вызов с `department=("ib", "tech"), stage=("presale", "implementation")` допускает все сочетания. Если нужны только пары `ib/presale` и `tech/implementation`, backend вызывает поиск по каждой паре и объединяет кандидатов по `source_id`. Отдельные вызовы также позволяют проверить обе области, если кандидаты одной из них заняли все первые `top_k` мест.
- Фильтр исключает явно несовпадающую область. Пункты регламента с неизвестной областью могут остаться кандидатами. Backend проверяет область применения по содержанию, прежде чем использовать пункт как основание для ответа.
- Начальное ранжирование — BM25. Добавление смыслового поиска сохраняет форму запроса и результата.
- Метод возвращает список `SearchResult` в порядке убывания `score`. Пустой список означает, что поиск успешно завершился без кандидатов. Технический сбой чтения, доступа или работы индекса передаётся через `RetrievalError`. Причина ошибки может быть доступна в техническом журнале.
- `score` — конечное число, большее значение означает более высокий ранг в текущей выдаче. Шкала зависит от поиска. Оценка не является вероятностью правильного ответа.

| Поле | Значение |
| --- | --- |
| `source_id` | Стабильный идентификатор цитируемого фрагмента. Для регламента формат — `regulation:<document_id>:<section>`. Retrieval использует исходную нумерацию с полным путём пункта, если номера повторяются в разных разделах. Ненумерованный список или таблица относится к содержащему их пункту. Фрагмент без проверяемого пункта не используется как точная ссылка. Для разъяснения backend назначает постоянный идентификатор записи, сохраняющийся при редактировании. Пространства идентификаторов двух видов источников не пересекаются. |
| `source_type` | `regulation` или `expert_answer`. |
| `document` | Отображаемое название источника. |
| `document_id` | Стабильный идентификатор регламента, обязательный для `regulation`. У экспертного ответа поле равно `None`. |
| `section` | Исходный номер пункта для цитируемого регламента. У разъяснения указывается при наличии связанного пункта, иначе `None`. |
| `department`, `stage` | Идентификаторы области или `None`. Для регламента `None` означает, что область неизвестна. Для разъяснения значения копируются из подтверждённой области применения. |
| `text` | Исходный текст фрагмента вместе с относящимися к нему элементами списка или таблицы. Для дословной цитаты backend использует проверяемую подстроку этого поля. |
| `status` | `approved` для регламента с подтверждённой актуальностью или `unknown` при отсутствии такого подтверждения. Для экспертного ответа допустим только `approved`. Даты ZIP и редактирования Word статус не устанавливают. |
| `score` | Оценка для ранжирования кандидатов. |
| `source_url` | Доступная пользователю ссылка или `None`. Без URL интерфейс показывает название документа и пункт. Ссылки и номера страниц указываются только при наличии подтверждённого указателя в источнике. Поле для номера страницы в контракте отсутствует. |
| `expert_metadata` | Метаданные подтверждённого разъяснения. Для регламента поле равно `None`. |

## Метаданные и изменение индекса разъяснений

| Поле `ExpertAnswerMetadata` | Значение |
| --- | --- |
| `appeal_id` | Идентификатор исходного обращения. |
| `approved_at` | Дата и время подтверждения с часовым поясом. В JSON используется ISO 8601 в UTC. |
| `scope` | `department`, `stage` и дополнительные условия `conditions`. Пустое измерение означает явно утверждённое отсутствие ограничения по этому измерению. Backend проверяет дополнительные условия перед ответом и запрашивает уточнение при нехватке фактов. |
| `revision` | Положительная возрастающая ревизия для данного `source_id`. Backend выдаёт новую ревизию при публикации новой версии и отзыве. |

- `upsert_expert_answer(answer)` добавляет или полностью заменяет запись. `answer` имеет тип `ApprovedExpertAnswer`. Backend создаёт его после утверждения конкретной редакции уполномоченным сотрудником службы качества. Текст, область, ссылка и дата подтверждения относятся к одной редакции.
- `delete_expert_answer(source_id, revision)` исключает запись из поиска и сохраняет номер ревизии удаления. Более старое обновление игнорируется, даже если пришло после удаления. При повторной публикации требуется ревизия выше ревизии удаления.
- Операции возвращают `None` после применения или идемпотентного повтора. Для одного источника равные ревизии допустимы только при повторе той же операции с теми же данными. Расхождение для одной ревизии считается ошибкой синхронизации. При сбое обе операции выбрасывают `RetrievalError`. Сравнение и применение ревизии должны выполняться атомарно для источника.
- Черновики остаются в SQLite. Отзыв сразу меняет опубликованное состояние в SQLite и ставит удаление из индекса в очередь.
- До возврата `SearchResult` поиск сверяет ревизии экспертных кандидатов через синхронный `ExpertPublicationLookup.published_revisions(source_ids) -> dict[str, int]`, предоставляемый backend. Словарь содержит только текущие опубликованные ревизии, прочитанные из SQLite. Кандидат без записи в словаре или с другой ревизией отбрасывается до применения `top_k`. Успешный поиск без допустимых кандидатов возвращает `[]`. Если проверка публикации недоступна, поиск выбрасывает `RetrievalError`. Backend перед отправкой ответа повторно проверяет процитированные разъяснения, чтобы учесть отзыв, произошедший после поиска.
- Согласованное разъяснение применимо в пределах утверждённой области. При расхождении с регламентом применяются те же правила уточнения, что и для двух регламентов.

## Результат агента

Обычный результат представлен `AgentResult`. В JSON значения перечислений передаются строками, `source_ids` — массивом, отсутствующие необязательные поля — `null`. Для показа цитат backend связывает `source_ids` с результатами поиска, из которых взяты цитаты, и передаёт интерфейсу название, пункт и доступную ссылку. В кавычки можно помещать только текст, совпадающий с исходным фрагментом.

| Тип | Ожидаемые поля и поведение |
| --- | --- |
| `ANSWER` | `text` и хотя бы один идентификатор фактически использованного источника. |
| `CLARIFY` | `clarification_question` с одним вопросом о параметре, влияющем на ответ. Следующее сообщение продолжает тот же `dialogue_id` и заполняет ожидаемый параметр. |
| `NO_ANSWER` | `text` объясняет, каких сведений не хватает. `appeal_id` указывает на созданное или повторно использованное обращение. В `source_ids` можно указать ближайшие положения, если текст явно обозначает их как справочные. |
| `CONFLICT` | `text` описывает расхождение, которое нельзя разрешить уточнением подразделения или этапа, и предлагает обратиться в службу качества. `source_ids` содержит как минимум два конфликтующих источника. `appeal_id` заполняется только при наличии отдельно зарегистрированного обращения. |

Для всех типов обязателен `dialogue_id`. Типы данных задают форму обмена. Согласованность полей для конкретного результата проверяет backend перед отправкой ответа. Технические ошибки возвращаются отдельно от `AgentResult`. Предлагаемый ответ при временной недоступности поиска или Ollama — HTTP 503 с полями `code` и `message`. Пример кода — `RETRIEVAL_UNAVAILABLE`. Frontend предлагает повторить запрос.

## Последовательные уточнения

Backend хранит на протяжении незавершённого запроса исходный вопрос, подтверждённые подразделение и этап, последний уточняющий вопрос и параметр, который требуется заполнить. Ответ «Техническая дирекция» подтверждает `tech`. Следующий ответ «На реализации» подтверждает `implementation`, сохраняя `tech` и исходный вопрос. После каждого шага поиск выполняется заново. Если пользователь исправляет ранее указанный параметр, backend заменяет его. При явной смене темы backend сбрасывает параметры и ожидаемое уточнение перед обработкой нового запроса.

## Синтетические примеры

Ниже вымышленные документы и данные. Формат входа приведён как пример сообщения между frontend и backend. Первые три примера относятся к одному диалогу. После утверждения разъяснения повторный запрос о хранении получает подтверждённый ответ.

### CLARIFY

```json
{
  "input": {"dialogue_id": "demo-1", "message": "Кто принимает опытный макет?"},
  "output": {
    "result_type": "CLARIFY", "dialogue_id": "demo-1", "text": null,
    "source_ids": [],
    "clarification_question": "Какое подразделение ведёт проект — Дирекция ИБ или Техническая дирекция?",
    "appeal_id": null
  }
}
```

### Повторный CLARIFY

```json
{
  "input": {"dialogue_id": "demo-1", "message": "Техническая дирекция."},
  "output": {
    "result_type": "CLARIFY", "dialogue_id": "demo-1", "text": null,
    "source_ids": [],
    "clarification_question": "Речь о пресейле или о реализации проекта?",
    "appeal_id": null
  }
}
```

### ANSWER по регламенту

```json
{
  "input": {"dialogue_id": "demo-1", "message": "На реализации."},
  "search_result": {
    "source_id": "regulation:demo:2.1",
    "source_type": "regulation",
    "document_id": "demo",
    "document": "Демонстрационный регламент",
    "section": "2.1",
    "department": "tech",
    "stage": "implementation",
    "text": "Опытный макет принимает руководитель стенда.",
    "status": "unknown",
    "score": 6.2,
    "source_url": null,
    "expert_metadata": null
  },
  "output": {
    "result_type": "ANSWER", "dialogue_id": "demo-1",
    "text": "«Опытный макет принимает руководитель стенда.» См. п. 2.1 демонстрационного регламента. Актуальность регламента не подтверждена.",
    "source_ids": ["regulation:demo:2.1"],
    "clarification_question": null, "appeal_id": null
  }
}
```

### NO_ANSWER

```json
{
  "input": {"dialogue_id": "demo-2", "message": "Где хранить опытный макет после испытаний?"},
  "output": {
    "result_type": "NO_ANSWER", "dialogue_id": "demo-2",
    "text": "В доступных источниках место хранения не указано. Обращение DEMO-17 зарегистрировано.",
    "source_ids": [],
    "clarification_question": null, "appeal_id": "DEMO-17"
  }
}
```

### ANSWER после подтверждения разъяснения

После подтверждения запрос о хранении находит следующее разъяснение. Шкала `score` в примере условная.

```json
{
  "input": {"question": "Где хранить опытный макет после испытаний?"},
  "search_result": {
    "source_id": "expert_answer:demo:17",
    "source_type": "expert_answer",
    "document": "Демонстрационное разъяснение DEMO-17",
    "section": null,
    "department": null,
    "stage": "implementation",
    "text": "После испытаний опытный макет хранится в демонстрационном боксе.",
    "status": "approved",
    "score": 0.87,
    "source_url": null,
    "document_id": null,
    "expert_metadata": {
      "appeal_id": "DEMO-17",
      "approved_at": "2026-01-15T09:00:00Z",
      "scope": {"department": null, "stage": "implementation", "conditions": "Для опытных макетов после испытаний."},
      "revision": 1
    }
  },
  "output": {
    "result_type": "ANSWER", "dialogue_id": "demo-3",
    "text": "После испытаний макет хранится в демонстрационном боксе. См. разъяснение DEMO-17.",
    "source_ids": ["expert_answer:demo:17"],
    "clarification_question": null, "appeal_id": null
  }
}
```

### CONFLICT

```json
{
  "input": {"dialogue_id": "demo-4", "message": "Кто в Технической дирекции на этапе реализации подписывает акт испытаний макета?"},
  "output": {
    "result_type": "CONFLICT", "dialogue_id": "demo-4",
    "text": "Пункт 3.2 одного применимого регламента поручает подпись руководителю стенда, а пункт 5.1 второго — координатору испытаний. Оба положения относятся к Технической дирекции и этапу реализации. Обратитесь в службу качества.",
    "source_ids": ["regulation:demo:3.2", "regulation:demo-aux:5.1"],
    "clarification_question": null, "appeal_id": null
  }
}
```

## Что согласовать перед реализацией

- Начальный набор синонимов и размещение расширяемых справочников.
- Значения стабильных ID четырёх документов и реальные ссылки, если они доступны.
- Контрольные вопросы для оценки BM25 и последующего смыслового поиска.
- HTTP-маршруты и формат карточки источника для frontend.
