# Контракты интеграции

Backend получает объект, реализующий `shared.contracts.Retrieval`. Методы синхронные. Если обработчик FastAPI асинхронный, backend выносит блокирующие вызовы за пределы цикла событий. Retrieval импортирует общие типы из `shared.contracts`.

## Идентификаторы областей

| Измерение | Идентификатор | Название |
| --- | --- | --- |
| Подразделение | `ib` | Дирекция ИБ |
| Подразделение | `tech` | Техническая дирекция |
| Подразделение | `dbrct` | ДБРЦТ |
| Этап | `presale` | Пресейл |
| Этап | `implementation` | Реализация проекта |

Это начальные справочники. В Python идентификаторы — строки, неизвестное значение — `None`, в JSON — `null`. Новые идентификаторы и синонимы добавляются в согласованные справочники без изменения типов. Backend приводит пользовательские названия и синонимы к каноническим значениям перед поиском. Если синоним указывает на несколько значений, контекст остаётся неподтверждённым.

## Поиск

```python
ScopeFilter = str | tuple[str, ...] | None

def search_documents(
    self,
    question: str,
    top_k: int = 8,
    department: ScopeFilter = None,
    stage: ScopeFilter = None,
) -> list[SearchResult]: ...
```

- `question` — непустой текст запроса с учётом уточнений. `top_k` — положительное целое число, максимум результатов. Ошибочный аргумент отклоняется через `ValueError`. Backend проверяет аргументы до вызова.
- Каждый фильтр принимает один идентификатор, непустой кортеж возможных идентификаторов или `None` для поиска без ограничения по этому измерению. Внутри кортежа действует «или», между измерениями — «и». Пустой кортеж и идентификатор вне согласованного справочника отклоняются через `ValueError`.
- Вызов с `department=("ib", "tech"), stage=("presale", "implementation")` допускает все сочетания. Если нужны только пары `ib/presale` и `tech/implementation`, backend вызывает поиск по каждой паре и объединяет кандидатов по `source_id`. Отдельные вызовы также позволяют проверить обе области, если кандидаты одной из них заняли все первые `top_k` мест.
- Фильтр исключает явно несовпадающую область. Пункты регламента с неизвестной областью могут остаться кандидатами. Backend проверяет область применения по содержанию, прежде чем использовать пункт как основание для ответа.
- Начальное ранжирование — BM25. Добавление смыслового поиска сохраняет форму запроса и результата.
- Метод возвращает список `SearchResult` в порядке убывания `score`. Пустой список означает, что поиск успешно завершился без кандидатов. Технический сбой чтения, доступа или работы индекса передаётся через `RetrievalError`. Причина ошибки может быть доступна в техническом журнале.
- `score` — конечное число, большее значение означает более высокий ранг в текущей выдаче. Шкала зависит от поиска. Оценка не является вероятностью правильного ответа.

| Поле | Значение |
| --- | --- |
| `source_id` | Стабильный идентификатор цитируемого фрагмента. Для регламента формат — `regulation:<document_id>:<section>`. Retrieval использует исходную нумерацию с полным путём пункта, если номера повторяются в разных разделах. Ненумерованный список или таблица относится к содержащему их пункту. Фрагмент без проверяемого пункта не используется как точная ссылка. Для разъяснения backend назначает постоянный идентификатор записи, сохраняющийся при редактировании. Пространства идентификаторов двух видов источников не пересекаются. |
| `source_type` | `regulation` или `expert_answer`. |
| `document` | Отображаемое название источника. |
| `document_id` | Стабильный идентификатор регламента, обязательный для `regulation`. У экспертного ответа поле равно `None`. |
| `section` | Исходный номер пункта для цитируемого регламента. У разъяснения указывается при наличии связанного пункта, иначе `None`. |
| `department`, `stage` | Идентификаторы области или `None`. Для регламента `None` означает, что область неизвестна. Для разъяснения значения копируются из подтверждённой области применения. |
| `text` | Исходный текст фрагмента вместе с относящимися к нему элементами списка или таблицы. Для дословной цитаты backend использует проверяемую подстроку этого поля. |
| `status` | `approved` для регламента с подтверждённой актуальностью или `unknown` при отсутствии такого подтверждения. Для экспертного ответа допустим только `approved`. Даты ZIP и редактирования Word статус не устанавливают. |
| `score` | Оценка для ранжирования кандидатов. |
| `source_url` | Доступная пользователю ссылка или `None`. Без URL интерфейс показывает название документа и пункт. Ссылки и номера страниц указываются только при наличии подтверждённого указателя в источнике. Поле для номера страницы в контракте отсутствует. |
| `expert_metadata` | Метаданные подтверждённого разъяснения. Для регламента поле равно `None`. |

## Метаданные и изменение индекса разъяснений

| Поле `ExpertAnswerMetadata` | Значение |
| --- | --- |
| `appeal_id` | Идентификатор исходного обращения. |
| `approved_at` | Дата и время подтверждения с часовым поясом. В JSON используется ISO 8601 в UTC. |
| `scope` | `department`, `stage` и дополнительные условия `conditions`. Пустое измерение означает явно утверждённое отсутствие ограничения по этому измерению. Backend проверяет дополнительные условия перед ответом и запрашивает уточнение при нехватке фактов. |
| `revision` | Положительная возрастающая ревизия для данного `source_id`. Backend выдаёт новую ревизию при публикации новой версии и отзыве. |

- `upsert_expert_answer(answer)` добавляет или полностью заменяет запись. `answer` имеет тип `ApprovedExpertAnswer`. Backend создаёт его после утверждения конкретной редакции уполномоченным сотрудником службы качества. Текст, область, ссылка и дата подтверждения относятся к одной редакции.
- `delete_expert_answer(source_id, revision)` исключает запись из поиска и сохраняет номер ревизии удаления. Более старое обновление игнорируется, даже если пришло после удаления. При повторной публикации требуется ревизия выше ревизии удаления.
- Операции возвращают `None` после применения или идемпотентного повтора. Для одного источника равные ревизии допустимы только при повторе той же операции с теми же данными. Расхождение для одной ревизии считается ошибкой синхронизации. При сбое обе операции выбрасывают `RetrievalError`. Сравнение и применение ревизии должны выполняться атомарно для источника.
- Черновики остаются в SQLite. Отзыв сразу меняет опубликованное состояние в SQLite и ставит удаление из индекса в очередь.
- До возврата `SearchResult` поиск сверяет ревизии экспертных кандидатов через синхронный `ExpertPublicationLookup.published_revisions(source_ids) -> dict[str, int]`, предоставляемый backend. Словарь содержит только текущие опубликованные ревизии, прочитанные из SQLite. Кандидат без записи в словаре или с другой ревизией отбрасывается до применения `top_k`. Успешный поиск без допустимых кандидатов возвращает `[]`. Если проверка публикации недоступна, поиск выбрасывает `RetrievalError`. Backend перед отправкой ответа повторно проверяет процитированные разъяснения, чтобы учесть отзыв, произошедший после поиска.
- Согласованное разъяснение применимо в пределах утверждённой области. При расхождении с регламентом применяются те же правила уточнения, что и для двух регламентов.

## Результат агента

Обычный результат представлен `AgentResult`. В JSON значения перечислений передаются строками, `source_ids` — массивом, отсутствующие необязательные поля — `null`. Для показа цитат backend связывает `source_ids` с результатами поиска, из которых взяты цитаты, и передаёт интерфейсу название, пункт и доступную ссылку. В кавычки можно помещать только текст, совпадающий с исходным фрагментом.

| Тип | Ожидаемые поля и поведение |
| --- | --- |
| `ANSWER` | `text` и хотя бы один идентификатор фактически использованного источника. |
| `CLARIFY` | `clarification_question` с одним вопросом о параметре, влияющем на ответ. Следующее сообщение продолжает тот же `dialogue_id` и заполняет ожидаемый параметр. |
| `NO_ANSWER` | `text` объясняет, каких сведений не хватает. После отдельной регистрации клиент получает идентификатор обращения. В `source_ids` можно указать ближайшие положения, если текст явно обозначает их как справочные. |
| `CONFLICT` | `text` описывает расхождение, которое нельзя разрешить уточнением подразделения или этапа, и предлагает обратиться в службу качества. `source_ids` содержит как минимум два конфликтующих источника. `appeal_id` заполняется только при наличии отдельно зарегистрированного обращения. |

Для всех типов обязателен `dialogue_id`. Типы данных задают форму обмена. Согласованность полей для конкретного результата проверяет backend перед отправкой ответа. Технические ошибки возвращаются отдельно от `AgentResult`. Предлагаемый ответ при временной недоступности поиска или API модели — HTTP 503 с полями `code` и `message`. Пример кода — `RETRIEVAL_UNAVAILABLE`. Frontend предлагает повторить запрос.

## Последовательные уточнения

Backend хранит на протяжении незавершённого запроса исходный вопрос, подтверждённые подразделение и этап, последний уточняющий вопрос и параметр, который требуется заполнить. Ответ «Техническая дирекция» подтверждает `tech`. Следующий ответ «На реализации» подтверждает `implementation`, сохраняя `tech` и исходный вопрос. После каждого шага поиск выполняется заново. Если пользователь исправляет ранее указанный параметр, backend заменяет его. При явной смене темы backend сбрасывает параметры и ожидаемое уточнение перед обработкой нового запроса.

## Что согласовать перед реализацией

- Начальный набор синонимов и размещение расширяемых справочников.
- Значения стабильных ID четырёх документов и реальные ссылки, если они доступны.
- Контрольные вопросы для оценки BM25 и последующего смыслового поиска.
- HTTP-маршруты и формат карточки источника для frontend.

## API агента

| Метод и путь | Назначение |
| --- | --- |
| `GET /health` | Проверка SQLite и состояние поиска `demo`, `configured` или `disabled`. |
| `POST /dialogues` | Новый диалог. Возвращает `dialogue_id` и отдельный `access_token`. |
| `POST /dialogues/{dialogue_id}/messages` | Принимает `{"message":"…","context":"auto"}`. Возвращает `result` по общему контракту, использованные `sources`, метрики вызова и агрегат диалога. |
| `GET /dialogues/{dialogue_id}/messages` | История и агрегат по всему диалогу. `limit` задаёт размер страницы, `before` берётся из `next_before`. |
| `GET /docs`, `GET /openapi.json` | Интерактивная документация и схема API. |

Для операций с диалогом передавайте `Authorization: Bearer <access_token>`. Человек может создать диалог без учётной записи. Токен даёт доступ к конкретному диалогу, а SQLite хранит его хеш. `context: "new"` сбрасывает тему, `"follow_up"` продолжает предыдущую, `"auto"` распознаёт типичные короткие уточнения и связующие формулировки. Для неоднозначной фразы используйте явное значение. Сеанс сохраняет исходный вопрос, последние существенные уточнения и ожидаемое поле. После трёх уточнений или повторения вопроса без продвижения агент завершает попытку ответом `NO_ANSWER`. Результат сообщения содержит `turn_id`. Регистрация выполняется отдельным запросом, который возвращает ID обращения. Исходный `AgentResult.appeal_id` до регистрации пуст.

Запрос ограничен 16 КиБ, текст сообщения — 2000 символами. Лимиты по умолчанию допускают 12 отправок и отдельно 12 созданий диалогов в минуту на весь экземпляр базы, 100 сообщений на диалог и 80 попыток обращения к модели за скользящие 24 часа. Настройки запуска `AGENT_PER_MINUTE` и `AGENT_DAILY_ATTEMPTS` задаются переменными процесса. Перед обработкой SQLite резервирует доступные попытки. Пустая выдача формирует `NO_ANSWER` без обращения к модели. Лимит попыток ограничивает расход при ограниченном контексте и выходе до 512 токенов, но не задаёт точную сумму списания. Перед публикацией понадобятся отдельные лимиты для пользователей и ограничения на стороне провайдера.

HTTP 502 возвращается при непригодном результате модели или нарушении подтверждения источников. HTTP 503 означает недоступность поиска, хранилища или модели. Ошибка сохраняется отдельно от результата, а состояние незавершённого уточнения остаётся доступно для следующей попытки. Метрики считаются по всем зарегистрированным попыткам, включая неудачные. Если хотя бы одна попытка не вернула счётчик, соответствующая сумма токенов неизвестна. Для стоимости API показывает известные подытоги по валютам и число попыток с неизвестной стоимостью.

### Подключение реального поиска

Передайте реализацию через `create_app(retrieval=..., publications=...)`. Настройте один и тот же авторитетный `ExpertPublicationLookup` для поиска и агента. Он должен возвращать опубликованные ревизии из SQLite. Без проверки публикации разъяснения не используются. Дополнительные условия проверяются по явным фактам текущего диалога. История скрывает ответы, в которых найдено отозванное или заменённое разъяснение.

Адаптер должен возвращать полные самостоятельные фрагменты с точной нумерацией, нормализованными областями и стабильными идентификаторами. В запрос к модели попадает до восьми выдержек, до 1 400 символов на выдержку и 8 400 символов на весь набор. Для длинного пункта агент ищет значимую часть по словам вопроса и сохраняет соседнее предложение или абзац, если помещается. За выдержкой сохраняются ID исходного пункта и символьные смещения. Агент сверяет цитату и с выдержкой, и с оригиналом. Если безопасный релевантный фрагмент выделить не удалось, пункт не используется как доказательство. Если модель выбирает только разъяснение при наличии лексически близкого официального пункта, сервер отклоняет результат с `source_review_required`. Для настоящего поиска штатная конфигурация допускает только локальный OpenAI-совместимый адрес.

Модель выбирает пункты и приводит точные подстроки. Сервер сам показывает исходный фрагмент с метаданными и проверяет привязку цитаты к источнику. Это исключает добавление моделью новых фактов в текст ответа. Семантическая релевантность выбранного пункта и распознавание противоречий оцениваются моделью и требуют проверки на контрольных вопросах.

## Регистрация и API службы качества

Для пользовательских маршрутов используется токен диалога. `POST /dialogues/{id}/appeals` принимает `{"turn_id": 123}` из ответа на сообщение. Первый запрос возвращает HTTP 201, повтор для того же сообщения — HTTP 200 и ту же карточку. `GET /dialogues/{id}/appeals/{appeal_id}` возвращает статус и состояние уведомления. После технического сбоя обращение не создаётся. Лимит — три новых карточки на диалог и десять на экземпляр SQLite за скользящие 24 часа.

| Метод и путь | Действие |
| --- | --- |
| `GET /quality/appeals?status=…` | Список обращений с фильтром и параметрами `offset`, `limit`. |
| `GET /quality/appeals/{id}` | Карточка, снимок диалога, черновик, публикация и доставка. |
| `PATCH /quality/appeals/{id}/status` | Перевод в `in_work` или `closed`. Закрытие карточки само по себе не отзывает разъяснение. |
| `PUT /quality/appeals/{id}/draft` | Сохранение первой или следующей редакции. |
| `POST /quality/appeals/{id}/approve` | Утверждение черновика и постановка в индекс. |
| `POST /quality/appeals/{id}/revoke` | Отзыв и удаление из индекса. |
| `POST /quality/appeals/{id}/retry-index` | Повтор неудавшейся операции или переиндексация текущей ревизии. |
| `GET /quality/explanations` | Список активных разъяснений. |
| `GET /robots.txt` | Запрет индексации. |

Маршруты `/quality/*` требуют `Authorization: Bearer <QUALITY_ADMIN_SECRET>`. Для изменений передавайте текущий `version`. Устаревшая версия возвращает HTTP 409. Текущая публикация остаётся активной, пока редактируется отдельный черновик. После утверждения следующей ревизии старая сразу выключается. HTTP 202 при утверждении или отзыве означает, что синхронизация ещё не завершена. Задание индекса автоматически пробуется до трёх раз, после чего доступен ручной повтор.

Черновик принимает `text`, необязательные `department`, `stage` и `conditions`. При первом сохранении пропущенные подразделение и этап берутся из обращения, при редактировании — из предыдущей редакции. Условия записываются в формате `вид=учебный;цвет=синий`. Агент принимает отдельную строку `ключ=значение` или короткий ответ на адресное уточнение. Сопоставление выполняется по точному нормализованному совпадению. Прочие формулировки или выводы модели не считаются подтверждением условия.

### SMTP и операционные ограничения

При отключении SMTP карточка получает статус `disabled`. При включении с неполной или неверной конфигурацией — `not_configured`. При настроенном транспорте возможны `pending`, `sending`, `retry`, `sent`, `failed`, `uncertain`. Статус `sent` означает принятие SMTP-реле. Неопределённый исход после начала отправки не повторяется вслепую, чтобы избежать дубликатов. Письмо содержит ссылку на документацию API службы качества, если задан `PUBLIC_APP_URL`. Отдельной панели пока нет.

Для прототипа один секрет даёт одну настроенную личность `QUALITY_ADMIN_NAME`. После пяти неудачных попыток в минуту адрес блокируется на остаток окна. При развёртывании за прокси согласуйте корректную передачу IP от доверенного прокси. Токены и данные редактора передаются по HTTPS. Публичному клиенту следует выводить экспертный текст и цитаты как обычный текст.

### Подключение индекса разъяснений

Используйте `create_app(retrieval_factory=...)`. Фабрика получает backend-реализацию `ExpertPublicationLookup` и передаёт её в поисковый модуль. Поиск проверяет текущую ревизию перед возвратом эксперта, агент проверяет её повторно. Адаптер должен атомарно сравнивать ревизии, игнорировать старые записи, идемпотентно принимать точный повтор и сохранять номер последнего удаления при перезапуске.

Исходный вопрос и ответ хранятся в SQLite. `ApprovedExpertAnswer.text` содержит только утверждённый ответ. Синтетический индекс дополнительно использует `index_questions(source_ids)` для поиска по формулировке обращения. Для реального индекса необходимо согласовать источник этого поля отдельно от цитируемого текста, без изменения общего контракта.
