# Подключение поиска регламентов к backend

Для совместного запуска в одной рабочей копии нужны модуль retrieval из Issue #6 и backend из main с функцией create_app. Все команды выполняются из корня проекта. Поиск работает с локальными весами и готовым индексом. Укажите локальный сервер генерации с OpenAI-совместимым API, который выполняет вычисления на вашей машине. Для корпоративного корпуса требуется локальная обработка и у самого сервера генерации.

## Подключение

```python
from backend.main import create_app
from retrieval.agent_adapter import retrieval_factory

app = create_app(retrieval_factory=retrieval_factory)
```

Фабрика принимает один объект `ExpertPublicationLookup` (backend передаёт свой экземпляр Quality) и возвращает синхронный адаптер `Retrieval`. Каждый процесс приложения загружает снимок индекса и E5 при создании адаптера. При старте ошибка загрузки останавливает создание приложения. Между запросами экземпляр проверяет указатель CURRENT. При смене поколения поиск под блокировкой загружает согласованные метаданные, векторы и BM25. Веса повторно используются для той же модели и ревизии. Запросы одного экземпляра выполняются последовательно под RLock. Перезапуск читает готовое поколение. Повреждение текущего поколения вызывает ошибку, автоматического отката к старым источникам нет.

```python
search_documents(question: str, top_k: int = 8, department: ScopeFilter = None,
                 stage: ScopeFilter = None) -> list[SearchResult]
```

Backend формирует уточнённый вопрос и передаёт подтверждённые фильтры. Каждый фильтр допускает None, один согласованный ID или непустой кортеж. Адаптер возвращает дословный текст фрагмента, название, document_id, section, source_id, тип, статус, область, score и известный source_url. В контракте нет поля страницы. Для цитирования требуется проверяемый пункт. Если пункт разбит на несколько чанков, в выдачу входит один соответствующий запросу фрагмент. У повторяющихся номеров из разных разделов в идентификатор и section входит путь по заголовкам. Полный идентификатор имеет вид regulation:<document_id>:<section>. Ненумерованный текст без привязки к пункту недоступен агенту для точного цитирования.

Пустой список означает успешный поиск без пригодного источника. Некорректный фильтр или пустой вопрос дают ValueError. Техническая ошибка поиска и превышение лимита кодировщика для составного вопроса дают RetrievalError, который backend отображает как HTTP 503 retrieval_unavailable.

Метод search_with_context с теми же аргументами возвращает пару (результаты, контекст). Контекст содержит generation, candidates (включая альтернативы вне top_k) и relationships. Метки different_applicability, review_same_process и verify_applicability подсказывают, какие области и источники сравнить. Статус и основание берутся из локального реестра. Сейчас Agent вызывает search_documents. Предложение для Димы — опционально вызвать search_with_context в Agent._fetch вместо отдельного обычного поиска, применять связи в пределах одной generation и передавать агенту только нужные сведения об области и актуальности. Потенциальное расхождение требует проверки исходных цитат.

## Экспертные разъяснения

Quality передаёт утверждённый ApprovedExpertAnswer и исходный вопрос через index_questions(ids). Вопрос обращения неизменяем. BM25 и E5 индексируют вопрос вместе с ответом. В SearchResult.text попадает полный утверждённый ответ, а в expert_metadata — ID обращения, дата утверждения, ревизия и область с дополнительными условиями. Проверку условий по фактам диалога выполняет агент.

Файл experts.sqlite3 рядом с CURRENT хранит текст, исходный вопрос, локальный вектор, SHA-256 содержимого и последнюю ревизию каждого source_id. Для ревизии, меняющей только метаданные, используется существующий вектор. Поле автора утверждения остаётся в SQLite службы качества. Контракт ApprovedExpertAnswer передаёт время, обращение, ревизию и область применения. Обновление и отметка об отзыве записываются транзакционно. Устаревшую операцию можно безопасно доставить повторно. Равная ревизия требует идентичного действия и утверждённых данных. Ошибка вычисления или записи откатывает транзакцию; очередь Quality может повторить операцию. Отзыв удаляет текст и вектор из действующей строки и сохраняет номер удаления для защиты от поздних публикаций.

При запросе адаптер сверяет экспертные ревизии с Quality.published_revisions до ранжирования и top_k. Сбой проверки возвращает RetrievalError. После отбора кандидатов backend проверяет цитируемые разъяснения повторно. Если в лимит выдачи и бюджет текста помещаются релевантный регламент и разъяснение, адаптер передаёт оба отдельными источниками. Агент проверяет дополнительные условия по фактам диалога и определяет, нужно ли уточнять вопрос или сообщать о противоречии. Векторы экспертов и регламентов используют одну модель; при изменении модели экспертные векторы перестраиваются из локальных данных. Длинные разъяснения кодируются несколькими проходами с проверкой длины и нормализацией среднего вектора. Это поиск по всей публикации, точность для длинных многотемных ответов требует отдельной оценки.

При переносе стенда сохраняйте полный каталог индекса и базу Quality из одного согласованного состояния при остановленных процессах. Проверка retrieval.index --check проверяет поколение регламентов. Отдельную базу экспертов проверяют тестом публикации, обновления, перезапуска и отзыва через Quality. Для синтетической проверки с настоящей E5 выполните `$env:TEST_LOCAL_E5 = "1"` и `& $py -m unittest discover -s tests -p test_agent_retrieval.py`.

## Локальная подготовка и запуск

```powershell
$py = '.\.venv\Scripts\python.exe'
& $py -m pip install -r requirements.txt -r requirements-retrieval.txt
$docs = '.\data\documents'
$registry = '.\data\registry.json'
$env:RETRIEVAL_INDEX = '.\data\index'
$env:RETRIEVAL_MODEL_ROOT = '.\models'
New-Item -ItemType Directory -Force $docs | Out-Null
if (-not (Test-Path $registry)) {
    & $py -m retrieval.metadata --documents $docs --draft $registry
    if ($LASTEXITCODE) { throw 'Ошибка подготовки реестра' }
}
```

Поместите ровно четыре исходных регламента DOCX в data/documents до создания черновика. Презентацию задания и остальные материалы храните за пределами этого каталога. Для первого запуска на машине без весов выполните следующую команду после установки зависимостей. Она скачивает только файлы публичной модели фиксированной ревизии. На машине с подготовленными весами этот шаг пропускается.

```powershell
& $py -c "from huggingface_hub import snapshot_download; from retrieval.embeddings import MODEL, REVISION, MODEL_ROOT; snapshot_download(MODEL, revision=REVISION, local_dir=MODEL_ROOT/MODEL/REVISION, allow_patterns=['*.json','sentencepiece.bpe.model','model.safetensors','1_Pooling/config.json'])"
```

Сначала поместите DOCX в каталог документов, затем сформируйте черновик. Перед построением проверьте реестр локально по образцу docs/registry.example.json и подтвердите только известные поля. Для повторного построения используйте тот же проверенный реестр.

```powershell
& $py -m retrieval.index --documents $docs --registry $registry --index $env:RETRIEVAL_INDEX --model-root $env:RETRIEVAL_MODEL_ROOT
if ($LASTEXITCODE) { throw 'Ошибка построения индекса' }
& $py -m retrieval.index --index $env:RETRIEVAL_INDEX --check
if ($LASTEXITCODE) { throw 'Ошибка проверки индекса' }
$env:LLM_BASE_URL = 'http://127.0.0.1:11434/v1'
$env:LLM_MODEL = Read-Host 'ID уже запущенной локальной модели'
# Для локального сервера без аутентификации SDK требует непустой ключ.
$env:LLM_API_KEY = 'local'
& $py -m uvicorn retrieval.agent_adapter:create_local_app --factory --host 127.0.0.1 --port 8000
```

Адрес выше подходит для локального сервера на порту 11434. Для сервера с авторизацией задайте его ключ локально. Необязательный QUALITY_ADMIN_SECRET открывает административные маршруты. Этот способ запуска оставляет SMTP выключенным. SQLite диалогов хранится в storage/. Для начальной проверки откройте http://127.0.0.1:8000/health и убедитесь, что retrieval равен configured. Интерактивное описание HTTP API доступно в /docs.

## Три сценария приёмки

В новом окне PowerShell выполните следующий блок. Для каждого независимого сценария создайте новый диалог. Храните токен и ответы локально.

```powershell
$api = 'http://127.0.0.1:8000'
$d = Invoke-RestMethod "$api/dialogues" -Method Post
$headers = @{Authorization = "Bearer $($d.access_token)"}
$url = "$api/dialogues/$($d.dialogue_id)"
function Ask([string]$message) {
    $body = @{message=$message} | ConvertTo-Json -Compress
    Invoke-RestMethod "$url/messages" -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
}
$r = Ask (Read-Host 'Введите проверочный вопрос')
$r.result
```

1. Выберите вопрос с заранее известным номером пункта. Для ANSWER сверьте цитату, документ и номер с локальным оригиналом.
2. Выберите процесс с разными правилами в двух подразделениях. После CLARIFY в том же диалоге выполните `$r = Ask 'Техническая дирекция'`. Сверьте область и источник. При сохраняющемся реальном противоречии проверьте CONFLICT и обе ссылки.
3. Задайте вопрос без основания в корпусе. После NO_ANSWER (или CONFLICT) зарегистрируйте обращение явно. Повтор для того же turn_id должен вернуть ту же карточку.

```powershell
Invoke-RestMethod "$url/appeals" -Method Post -Headers $headers -ContentType 'application/json' -Body (@{turn_id=$r.turn_id} | ConvertTo-Json)
```

Для регрессии на синтетических данных запустите тесты в совместной копии.

```powershell
$env:TEST_LOCAL_E5 = '1'
$env:TEST_LOCAL_RERANK = '1'
& $py -m unittest discover -s tests
```
