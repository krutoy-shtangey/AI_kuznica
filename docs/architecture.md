# Архитектура агента ИИКузница

Агент отвечает на вопросы сотрудников по четырём регламентам DOCX и подтверждённым разъяснениям службы качества. Он указывает конкретные пункты, уточняет подразделение и этап проекта по ходу диалога и регистрирует обращения, когда обоснованного ответа нет.

## Компоненты и ответственность

| Каталог | Владелец | Компонент и границы |
| --- | --- | --- |
| `retrieval/` | Даша, `feature/retrieval` | Загрузка DOCX, извлечение пунктов, вложенных списков и таблиц, метаданные, индекс, поиск и операции с индексом разъяснений. |
| `backend/` | `feature/assistant` | Python 3.11 и FastAPI. Диалоги, маршрутизация запросов, проверка применимости и источников, обращения, согласование разъяснений и вызов локальной модели через Ollama. |
| `frontend/` | `feature/assistant` | React и Vite. Чат, отображение источников и обращений, экран службы качества для согласования ответов. Связь с FastAPI по HTTP/JSON. |
| `shared/` | Оба разработчика | Общие Python-типы и интерфейс поиска. Зависимости только из стандартной библиотеки. |
| `docs/` | Оба разработчика | Архитектура и договорённости об интеграции. |

FastAPI вызывает retrieval через синхронный Python-интерфейс. Начальное ранжирование использует BM25. Смысловой поиск подключается позже за тем же интерфейсом. Retrieval возвращает кандидатов и метаданные. Backend управляет диалогом и проверяет, какие кандидаты пригодны для ответа. Ollama получает необходимые фрагменты локально и помогает сформулировать краткий ответ. Конкретная модель выбирается позже.

SQLite хранит диалоги, сообщения, исходный вопрос незавершённого запроса, подтверждённые параметры, ожидаемое уточнение, обращения, версии экспертных ответов и задания синхронизации индекса. Правила индексации и его движок находятся в зоне ответственности retrieval. Типы и правила обмена описаны в [контрактах интеграции](integration.md).

## Обработка сообщения

1. Backend загружает диалог по `dialogue_id`. При продолжении уточнения он сохраняет исходный вопрос, привязывает короткий ответ к ожидаемому параметру и обновляет только этот параметр. Исправление пользователя заменяет указанное значение. При явной смене темы backend начинает новый запрос в том же диалоге.
2. Retrieval ищет по исходному вопросу с учётом подтверждённых параметров. Если возможны несколько подразделений или этапов, backend передаёт несколько идентификаторов. Стартовый справочник — `ib`, `tech`, `dbrct` для подразделений и `presale`, `implementation` для этапов. Неизвестное значение передаётся как `None`. Справочники и синонимы расширяемы.
3. Если для выбора применимого правила требуется факт от пользователя, агент возвращает `CLARIFY` с одним вопросом. Следующее сообщение уточняет исходный запрос. Если применимое правило однозначно и покрывает вопрос, агент возвращает `ANSWER` с точными цитатами из исходного текста при необходимости. Для регламента источник указывается по стабильному ID документа и номеру пункта. Если актуальность регламента не подтверждена, его статус — `unknown`.
4. При расхождении агент сначала проверяет, поможет ли уточнение подразделения или этапа. Если поможет, он возвращает `CLARIFY` и повторяет поиск после ответа. Если противоречие сохраняется, агент возвращает `CONFLICT`, указывает источники и предлагает обратиться в службу качества. Если нужного основания нет и уточнение не поможет, backend создаёт или повторно использует обращение и возвращает `NO_ANSWER`. Повтор доставки одного сообщения не должен создавать дубликат обращения.
5. При техническом сбое пользователь получает сообщение об ошибке и возможность повторить запрос. Сбой сам по себе не является основанием для обращения в службу качества.

## Подтверждение разъяснений

Сотрудник службы качества готовит ответ на обращение, указывает область применения и при наличии связывает его с пунктом регламента. Конкретную редакцию утверждает только уполномоченный сотрудник службы качества. Backend сохраняет действие и задание обновления индекса в одной транзакции SQLite. Добавление, замена и отзыв используют возрастающие ревизии и синхронизируются с индексом с повтором при сбоях. До включения разъяснения в выдачу retrieval сверяет его ревизию с опубликованной в SQLite через интерфейс чтения, предоставленный backend. Backend повторно проверяет состояние перед отправкой ответа. Если проверка недоступна, поиск завершается технической ошибкой.

## Развёртывание

Для последующего запуска предусмотрены Docker, локальный доступ backend к Ollama, постоянные локальные тома для SQLite и индекса и доступ к исходным DOCX в режиме чтения. В репозитории хранятся код и синтетические примеры. Регламенты, содержимое индекса и данные диалогов хранятся локально вне отслеживаемых Git файлов.
