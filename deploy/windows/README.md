# Windows 10: локальный демонстрационный сервер

Команды выполняются из корня AI_kuznica в PowerShell. Никаких Docker, Ollama или генеративных весов не требуется. Backend и собранный frontend работают на одном адресе http://127.0.0.1:8000. Порт слушает только loopback. Дизайн не меняется.

## Установка и запуск

Нужны Python 3.12, Node.js 22.12+ с npm и Git. Если они установлены после открытия терминала, откройте новое окно PowerShell.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\windows\setup.ps1
# Если нет Python Launcher, передайте полный путь к настоящему python.exe:
# .\deploy\windows\setup.ps1 -Python 'C:\path\Python312\python.exe'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\windows\app.ps1 Start
```

ExecutionPolicy Bypass действует только для этого процесса; системная политика не изменяется. setup.ps1 создаёт отдельную .venv и выполняет pip install, npm ci и production-сборку. Существующую .venv macOS переносить нельзя. При сбое установки скрипт останавливается с ошибкой. Встроенный Python среды Codex подходит для подготовки, но для независимого домашнего сервера установите постоянный Python 3.12 вне кеша Codex.

| Команда после `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\windows\app.ps1` | Действие |
| --- | --- |
| `Start` | Фоновый запуск demo-offline и проверка HTTP |
| `Stop` | Остановка управляемого процесса |
| `Restart` | Остановка и повторный запуск |
| `Status` | Health, PID и рабочая память процессов |
| `Logs` | Последние 80 строк |
| `Logs -Follow` | Непрерывный просмотр журнала |
| `Run -Mode demo-offline` | Supervisor на переднем плане, в том числе для Планировщика |
| `Start -Mode disabled` | Интерфейс и API без поиска |
| `Backup` | Согласованная копия остановленного сервера |

Проверка: `Invoke-RestMethod http://127.0.0.1:8000/api/health`. В offline-демо ожидается `retrieval: demo`; браузер показывает «Демонстрационный режим». Наличие server.json само по себе не доказывает работоспособность: проверяйте HTTP и процессы через Status.

demo-offline использует синтетический поиск и детерминированные ответы только для учебного корпуса. Это не свободная языковая модель и не поиск по настоящим документам. Настройки ProxyAPI в .env сохранены, но этот launcher не создаёт клиент LLM и не загружает SMTP. Даже SMTP_ENABLED=1 в .env не включает отправку через него. Режимы retrieval и произвольные строки отклоняются; автоматического переключения на демонстрационные источники нет.

Примеры вопросов:

1. «Кто принимает опытный макет?» → «Техническая дирекция» → «На реализации».
2. «А где фиксируют приёмку опытного макета?» — дополнительный вопрос.
3. «Кто подписывает акт испытаний опытного макета в Технической дирекции на реализации?» — конфликт.
4. «Кто выдаёт пропуск в зал маяка?» — отсутствие ответа, создание обращения.

Для службы качества используйте QUALITY_ADMIN_SECRET из локального .env. Он не печатается скриптами и не передаётся в аргументах процесса. Не публикуйте секрет и токены диалогов. Подтверждение и отзыв в demo-offline изменяют только демонстрационный индекс. Для проверки экспертного разъяснения используйте тот же вопрос в новом диалоге.

## Данные и настоящий поиск

| Путь относительно корня | Содержимое |
| --- | --- |
| `.env` | Существующие секреты; значения не меняются |
| `storage/windows/storage/demo.sqlite3` | Постоянная демонстрационная база, включая очередь и лимиты |
| `storage/windows/storage/maintenance.sqlite3` | Отдельная база режима disabled |
| `storage/windows/documents` | Четыре DOCX, без PDF задания |
| `storage/windows/index` | Место для согласованного поискового индекса |
| `storage/windows/models` | Место для E5; сейчас веса отсутствуют |
| `storage/windows/run` | Состояние supervisor и сигнал остановки |
| `logs/windows` | Журналы сервера и supervisor |
| `backups` | Закрытые архивы SQLite, документов, индекса и E5 |

Секреты, исходный архив, документы, индексы, SQLite, модели, журналы и резервные копии исключены из Git. Сам .gitignore не защищает от принудительного git add -f; не используйте его для данных.

На момент переноса в текущей feature/assistant каталога retrieval нет. Локально сохранённая origin/feature/retrieval содержит retrieval/agent_adapter.py, requirements-retrieval.txt, документацию и тесты. Ветка не объединялась, актуальность относительно сервера GitHub не проверена. По статическому чтению адаптер принимает ExpertPublicationLookup, реализует upsert/delete с ревизиями и использует index_questions. Исполнение, качество корпуса и финальность модуля ещё не проверены.

После отдельно согласованной интеграции следуйте docs/retrieval-agent.md именно из принятого выпуска. Установите закреплённый там torch из официального CPU-индекса https://download.pytorch.org/whl/cpu **перед** requirements-retrieval.txt. В сохранённой ветке закреплён torch==2.9.1. Проверьте `torch.version.cuda is None`, задайте RETRIEVAL_INDEX и RETRIEVAL_MODEL_ROOT абсолютными путями к каталогам выше. E5 в адаптере работает на CPU; не скачивайте генеративные модели или дополнительные reranker-модели без необходимости.

Сначала создаётся черновик локального реестра, затем проверяются только достоверно известные метаданные, строится и проверяется индекс. Команды из docs/retrieval-agent.md применяются после интеграции; сейчас их запуск завершится отсутствием модуля. Нельзя объявлять регламент действующим без основания.

Существующий backend запрещает внешний LLM для корпоративного поиска. Мы сохраняем этот запрет. Для ProxyAPI с настоящими регламентами нужны разрешение на конкретные данные и отдельное ограниченное изменение проверки внешнего endpoint. Простая подстановка URL и общий флаг разрешения небезопасны. Синтетический деморежим не подтверждает готовность настоящего поиска.

## Тесты без оплаты и писем

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
npm.cmd --prefix frontend run build
npm.cmd --prefix frontend exec playwright install chromium
npm.cmd --prefix frontend test
```

Для уже установленного Google Chrome можно вместо загрузки Chromium задать `$env:UI_TEST_CHROME='1'`. Браузерные тесты запускают свои процессы на 8117 и 5178 и свою временную SQLite. Проверка production использует собранные файлы и один origin 8117. Они не используют рабочую базу сервера на 8000. FixtureModel и FailedMail исключают платные вызовы и настоящие письма. Backend-тесты используют подставные клиенты.

Дополнительные проверки: test_windows_launcher.py проверяет режим, закрытую админку, отсутствие клиентов LLM/SMTP, изоляцию и восстановление диалога после пересоздания приложения. test_state.py проверяет SQLite WAL и восстановление индекса, запрет перезаписи архива и небезопасные Windows-пути.

## Автозапуск и восстановление

Системные задания сейчас не создавались. Когда локальная проверка пройдена, откройте Планировщик заданий → Создать задачу. Выберите своего пользователя без повышения привилегий, триггер «При запуске компьютера» с задержкой 30 секунд и выполнение независимо от входа пользователя (Windows запросит его пароль). Альтернатива без сохранения пароля — триггер «При входе в систему», но до входа сервер не запустится.

Действие: программа `powershell.exe`, аргументы:

```text
-NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File "D:\КУЗНИЦА\AI_kuznica\deploy\windows\app.ps1" Run -Mode demo-offline
```

Рабочая папка: `D:\КУЗНИЦА\AI_kuznica`. В параметрах задачи: перезапуск при сбое через минуту (до трёх попыток), не запускать второй экземпляр, убрать ограничение длительности выполнения. Туннель в задание не включать. После принятия реального поиска конфигурацию задачи нужно отдельно пересмотреть.

Supervisor удерживает межпроцессную блокировку и перезапускает упавший Uvicorn с задержкой, максимум пять последовательных коротких сбоев. После минуты работы счётчик сбрасывается. Порт, занятый другим приложением, вызывает отказ; чужие процессы не останавливаются. Это восстановление после завершения процесса, а не обнаружение зависаний. Для зависшего HTTP проверьте Status/Logs и выполните Restart. Stop использует сигнальный файл; текущий HTTP-запрос может прерваться. SQLite восстанавливается из WAL, незавершённые задания нужно проверить после запуска.

## Сон и обслуживание Windows

Настройки не изменялись. При отдельном подтверждении оператора: Параметры → Система → Питание и спящий режим → сон при питании от сети «Никогда». Экран можно выключать. Проверьте также гибернацию и дополнительные параметры питания. Не отключайте обновления, брандмауэр или защиту Windows; планируйте перезагрузки вне демонстрации. Компьютер должен оставаться включённым и подключённым к интернету, питание и домашний провайдер остаются точками отказа.

## Резервная копия и восстановление

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\windows\app.ps1 Stop
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\windows\app.ps1 Backup
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\windows\app.ps1 Start
```

Остановите также все отдельные процессы индексации/обслуживания и запланированную задачу, чтобы они не запустились во время копирования. Не копируйте живой SQLite одним Copy-Item. deploy.state применяет SQLite Backup API и quick_check и архивирует storage/documents/index/models из остановленного состояния. База и полный индекс, включая experts.sqlite3 и CURRENT, должны восстанавливаться вместе. Убедитесь, что архив появился, скопируйте его на защищённый внешний носитель. Он содержит корпоративные данные. .env не включён: храните отдельную зашифрованную копию секретов.

Проверяйте восстановление в новый отсутствующий каталог, не поверх работающего состояния:

```powershell
.\.venv\Scripts\python.exe -B -m deploy.state restore --state-dir 'D:\КУЗНИЦА\AI_kuznica\storage\restore-check' --archive 'D:\КУЗНИЦА\AI_kuznica\backups\ИМЯ.tar.gz'
```

После проверки остановите задачу и приложение, сохраните старый storage/windows, замените каталоги данных согласованным восстановленным набором и запустите сервер. Не переносите runtime-файлы run между машинами. После готовности поиска дополнительно выполняйте его --check и полный цикл публикации/отзыва эксперта.

## ngrok — только после отдельного разрешения

Установленный через Microsoft Store ngrok находится по `%LOCALAPPDATA%\Microsoft\WindowsApps\ngrok.exe`. Проверяйте без открытия туннеля:

```powershell
& "$env:LOCALAPPDATA\Microsoft\WindowsApps\ngrok.exe" version
& "$env:LOCALAPPDATA\Microsoft\WindowsApps\ngrok.exe" config check
```

На бесплатном плане аккаунту выдаётся один постоянный dev-домен: он сохраняется между перезапусками, имя выбирает ngrok. Собственное имя/домен требует другого тарифа. Есть квоты и промежуточная предупреждающая страница. Источники: https://ngrok.com/docs/gateway/domains/ и https://ngrok.com/docs/pricing-limits/free-plan-limits/ . Условия проверены 27.11.2026; перед показом проверьте доступный домен и остатки квот в своём аккаунте.

Дальнейшие шаги выполняет оператор **после разрешения публичного доступа**: войти в ngrok Dashboard, взять authtoken, локально настроить агент по инструкции https://ngrok.com/docs/getting-started/ , затем проверить config check. Не отправляйте токен в чат, Git или журналы. Задавайте его через интерактивную локальную настройку; история команд с токеном тоже является секретом.

Подготовленная команда открытия туннеля (сейчас не выполнять):

```powershell
& "$env:LOCALAPPDATA\Microsoft\WindowsApps\ngrok.exe" http http://127.0.0.1:8000 --inspect=false
```

inspect=false отключает захват тел запросов локальным инспектором, но трафик всё равно проходит через ngrok. Не передавайте через него корпоративные данные без разрешения. Не включайте доверие произвольным X-Forwarded-For: запуск использует --no-proxy-headers, поэтому лимиты IP за туннелем сейчас общие для loopback. Для небольшого демо это безопасное ограничение; для нескольких пользователей отдельно настройте проверенную политику ngrok и лимиты. HTTPS-адрес и действующий токен не проверялись публичным запросом.

Перед публикацией нужны: успешные backend/браузерные тесты и production-сборка, выбранный разрешённый набор данных, интегрированный/проверенный поиск либо честно заявленное offline-демо, разрешение на внешний API, согласованная передача через ngrok, лимит расходов на стороне ProxyAPI, длинный административный секрет и проверенная резервная копия. Системные настройки, публичный доступ и SMTP этим набором скриптов не включаются.
